# Kirole BLE 两阶段联调与验收清单

**起点：** Build 640 / BLE v2.10.1

**目标：** 先用 Build 640 跑通临时在线链路，再用 Build 636 验收 BLE v2.18 固件。

**字节依据：** [《BLE 通信协议规格文档》v2.18.0](BLE通信协议规格文档.md)

> Build 640 来自固定标签 `release/build-640-629-baseline`，实际采用 Build 629 / BLE v2.10.1 在线路径。它只用于第一次联调，**不是量产包，也不代表 v2.18 已完成**。

## 1. Build 640 基线

先按下面这组已知行为联调，不把后续能力倒推到 640：

| Build 640 已有 | 实际行为 | 640 阶段边界 |
|---|---|---|
| 进任务 | 设备发 `0x10 EnterTaskIn`，App 回 `0x11 TaskInPage` | 验在线进任务和 5 秒兜底 |
| 完成 / 跳过 | 设备发严格 v1 `0x11/0x12`；App 回最终 `0x10 DayPack → 0x1B` | 验匹配确认和一次刷屏 |
| 刷新 | 设备发严格 v1 `0x20 RequestRefresh`，App 回匹配 `0x1B` | 不能只用“有没有 DayPack”判断成功 |
| 离线批次 | `0x20 EventLogRequest / 0x21 EventLogBatch` 只按 best-effort 观察 | 640 不要求空 `0x21` 完成连接屏障 |
| 上线通知 | 实时 `0x30 DeviceWake` payload 为 29B | 640 不验 51B Wake |

Build 640 不发送、不验收 `0x23`、`0x24`、51B Wake、断联专注、跨断电 outbox 或快照 NVS 自愈。

这张表是唯一施工总表。字段长度、CRC 和结果码不在这里重复，直接点主协议章节。

|---|---|---|---|---|---|

| 完成 / 跳过可幂等确认 | Device→App `0x11/0x12`；App→Device `0x1B` | OperationID 持久化、原样重发、收到匹配确认才清记录 | 给旧命令补离线和确认规则 | **否：补旧命令规则** | 保留原 Type 和 payload；同一动作重发必须复用原 OperationID 和字节；只有匹配 `0x1B` 才结束记录。见[§4.21](BLE通信协议规格文档.md#421-tasklistsnapshotack-0x1b) |
| 重连先收设备离线动作 | `0x20/0x21` 已有，但 640 只 best-effort | 每连接屏障、有界待回放集合、原始顺序、满队列处理 | 给旧命令补单批和持久化规则 | **否：补旧命令规则** | 每个 `0x20 EventLogRequest` 正好回一个完整逻辑 `0x21`：空队列 Count=0，非空一次带完，必要时走既有分包。整份待回放集合 MVP 建议 32 条 / 4096B，须由硬件实测签收；未确认任务动作永不淘汰，普通事件放不下时 best-effort 丢弃；清完普通事件仍满时才拒绝新任务动作并提示。见[§5.23](BLE通信协议规格文档.md#523-离线任务动作持久化幂等回放与回放优先v2160-wire-不变) |
| 设备本地有完整当天任务库 | `0x1B` 只有动作结果和 Overview，不是任务库 | 任务详情、三阶段文案、版本、CRC、原子 committed 库 | 单独传任务库事务 | **是：新增 `0x23`** | 实现完整/增量接收、校验、原子提交、失败保留旧库和同 Type 结果回报。见[§4.22](BLE通信协议规格文档.md#422-tasklibrarytransaction-0x23)、[§5.21](BLE通信协议规格文档.md#521-tasklibrarycommitresult-0x23) |
| 设备本地有当天日程和每日文案 | `0x10 DayPack` 已有日期、最多 8 条日程、SupportText、DaySummary 和结算文案，也可原子保存最后一个完整包 | 若要完整匹配 Build 636，还缺独立版本/ACK、早/闲/晚三套对话、逐事件 CompanionDialogue、屏保作者 | 如果只把日程上限提到 20，可保持 `0x10` wire 结构不变，只改 App 截取上限和固件容量；最坏 payload 约从 3.4KB 增到 7KB，须真机确认；若要完整离线内容事务，再用 `0x24` | **只加条数：修改旧 `0x10` 规则；完整路线：新增 `0x24`** | `0x24` 与任务库分区保存；完整校验后一次提交；坏 CRC、坏版本、容量不足都保留旧内容。见[§4.23](BLE通信协议规格文档.md#423-dailycontenttransaction-0x24)、[§5.22](BLE通信协议规格文档.md#522-dailycontentcommitresult-0x24) |
| 断联后专注继续 | `0x10 EnterTaskIn`、`0x14 FocusStatus`、`0x20 RequestRefresh` 已有 | 本地专注任务、RTC 计时、阶段文案、重连恢复和息屏唤醒 | 给旧命令补本地状态规则 | **否：补旧命令规则** | 仍发入站 `0x10`，但从 committed 任务库立即进专注，不再等 App 的 `0x11 TaskInPage`；断联不退页、不清零；连接中约 5 分钟发 `0x20`，让 App 回最新 `0x14`。见[§5.7](BLE通信协议规格文档.md#57-requestrefresh-0x20)、[§9.6](BLE通信协议规格文档.md#96-断联专注连续性与当前任务编辑锁v2160-wire-不变) |
| 重启后 App 知道设备真实库存 | 29B 实时 `0x30` 只报电量、固件和头像库存 | 任务库库存、`0x1B` 快照 Epoch/Revision、12B NVS CRC | 扩展同一条上线通知 | **否：扩展旧命令 `0x30` 到 51B** | 成功应用 `0x1B` 时原子保存 SnapshotEpoch/Revision/CRC；实时 Wake 报任务库和快照库存；坏记录报 missing。批次内 Wake 记录仍是两字节。见[§5.8](BLE通信协议规格文档.md#58-devicewake-0x30--设备上线通知--wake-notify) |
| BLE 常开又省电 | 普通扫描、连接和 GATT 已有 | 屏保/低功耗下持续可连接、连接参数和电源配置 | 用 ESP32 电源管理解决 | **否；`0x25` 不做** | 屏保/低功耗下仍响应 GATT；实测连接电流和续航；不增加唤醒命令。见[§2.5](BLE通信协议规格文档.md#25-ble-常开与设备低功耗v2170-新增) |

最小结论：

- 5 秒兜底和 EPD 合并/单刷：不改字节。
- `0x11/0x12 + 0x20/0x21 + 0x1B`：复用旧命令，只补规则。
- 完整任务库：新增 `0x23`。
- 当天内容：新增 `0x24`。
- 库存与快照恢复：实时 `0x30` 从 29B 扩到 51B。
- `0x25`：撤销，不做。

### 2.1 产品如果还要继续缩 MVP 范围

默认仍建议完整匹配 Build 636：`0x23 + 0x24 + 51B 0x30`。这些 App 能力已经写完并有测试，保留它们不需要再造一个中间 App 协议。

只有产品明确接受以下损失时，才把 `0x24` 和 51B 任务库/快照库存自愈后置：

- 固件只原子保存最后一个完整 DayPack（最多 8 条日程），同内容不重复擦写，并用本地模板补早/闲/晚、屏保或逐事件文案；不验收独立当天内容事务。
- 测试阶段允许任务库或 `0x1B` 快照库存清空/损坏后人工清状态；不验收 51B `0x30` 提供的选择性自愈。
- App 必须另出一个**单协议**新构建：`0x23` 先只发 full；取消 `0x24` 发送/ACK 硬等待；每次重连回放后强制重发当天 `0x10`，必要时重发 `0x16`；若产品只要 20 条日程，可把 `0x10` 的 App 截取上限从 8 改为 20，但要先确认固件内存和传输时间。不能直接拿未修改的 Build 636，也不做运行时自动猜协议。

这三条没有产品、App、固件三方签字时，仍按完整 Build 636 路线验收。

## 5. 明确不做

- **不做 `0x25 DevicePowerControl`。** BLE 常开和省电只靠设备电源管理、连接参数和 GATT 正常响应。
- **不为完成、跳过、回放另造新命令。** 复用 `0x11/0x12 + 0x20/0x21 + 0x1B`。
- **一个 `0x20 EventLogRequest` 只对应一个完整逻辑 `0x21`。** 不增加第二套批次状态。
- **整份待回放集合达到双方签收上限时，不覆盖未确认任务动作。** 普通事件只做 best-effort；清完普通事件仍满时不静默接受下一任务动作。默认建议 32 条 / 4096B，硬件确认前不把建议值写成实测事实。
- **Build 640 不补成量产包。** 它不验 `0x23`、`0x24`、51B Wake、断联专注或跨断电自愈。
- **不把 App 日志或模拟器通过写成固件已完成。** NVS、RTC、EPD、BLE 功耗和断电恢复都必须真机留证据。
