### 1. 断连期间设备行为

- BLE 断连后，只有设备按键长按/短按可以进入或退出专注。
- 按键操作在设备端立即生效，不等待 App 确认。
- 每次操作写入离线队列，并分配唯一 `OperationID`。
- 重连后 App 必须先完成专注状态裁决，不能立即用断连前缓存的 `FocusStatus` 覆盖设备状态。
- 同一专注过程通过 `FocusSessionId` 关联进入、退出、计时和结算。
- 设备与 App 计时偏差不超过 120 秒时按正常误差处理，不新建会话。
- 同一会话出现 `active/end` 冲突时，以结束状态优先。

### 2. 新增命令字

| 方向 | Type / Opcode | 命令 | Payload | 说明 |
|---|---|---|---:|---|
| Device → App | `0x25 / 0x83` | `FOCUS_STATE` | `37+N` | 上报设备当前或待裁决的专注快照 |
| App → Device | `0x25 / 0x06` | `FOCUS_RESOLVE` | `33` | App 下发最终专注裁决 |
| Device → App | `0x25 / 0x81` | `RESULT` | `7` | 返回 `FOCUS_RESOLVE` 的执行结果 |

所有多字节整数均使用 Big Endian。

#### FOCUS_STATE（0x83）

主要字段：

- `FocusRevision`：设备当前专注版本。
- `BootSessionId`：设备启动会话 ID。
- `FocusSessionId`：本次专注会话 ID。
- `FocusState`：`idle / active / endedPending`。
- `StartSource`：App 在线建立或设备离线建立。
- `TaskId`：关联任务。
- `StartTimestamp / EndTimestamp`：设备记录的开始、结束时间。
- `ElapsedSeconds`：设备累计专注秒数。
- `LastOperationID`：最近一次相关离线操作。
- `EndReason`：完成、跳过或 App 结束。

App 收到 `FOCUS_STATE` 后仍需保持专注同步锁定，不能立即发送普通 `FocusStatus`。

#### FOCUS_RESOLVE（0x06）

主要字段：

- `ResolveID`：本次裁决 ID，必须非零；超时重试必须复用相同值和相同 payload。
- `FocusSessionId`：最终采用的专注会话。
- `FocusState`：最终权威状态。
- `ResolveResult`：App 的裁决类型。
- `StartTimestamp / EndTimestamp / ElapsedSeconds`：权威时间。
- `FocusRevision`：裁决后的权威版本。
- `Phase / Bottles`：根据权威时长重新计算，不能把 App 和设备数值相加。

`ResolveResult` 取值：

- `0x00 accepted`：接受设备状态。
- `0x01 closed`：结束优先，会话已关闭。
- `0x02 conflictResolved`：不同活动会话已完成归并。
- `0x03 rejected`：裁决失败，设备保留状态和队列。
- `0xFF internalError`：App 内部错误，设备保留并等待重试。

### 3. 补充 RESULT 应答闭环

`FOCUS_RESOLVE` 处理完成后，设备必须返回：

```text
Type      = 0x25
Opcode    = 0x81
SyncId    = 对应 FOCUS_RESOLVE 的 ResolveID
TargetType= 0x25
ResultCode
```

`ResultCode` 处理规则：

| ResultCode | 名称 | App 行为 |
|---:|---|---|
| `0x02` | `COMMITTED` | 裁决已应用；三个匹配条件满足后解除锁定 |
| `0x00` | `ACCEPTED` | 请求已接收但裁决未落地，不解除锁定 |
| `0x10` | `INVALID_STATE` | 状态或版本冲突，重新查询状态后裁决 |
| `0x13` | `INVALID_PAYLOAD` | 请求字段非法，修正后重试 |
| `0xFF` | `INTERNAL_ERROR` | 设备内部错误，不解除锁定 |

App 只有同时满足以下条件才能解除 `focusSyncLocked`：

```text
SyncId == 本次 ResolveID
TargetType == 0x25
ResultCode == COMMITTED（0x02）
```

`FOCUS_RESOLVE` 中的 `ResolveResult` 是 App 给出的裁决结论；`RESULT` 中的 `ResultCode` 是设备对该裁决的执行应答，两者不能混用。

### 4. 复用及扩展的命令

| Type / Opcode | 命令 | 本次变化 |
|---|---|---|
| `0x25 / 0x80` | `STATE` | 增加 `FocusSyncPending(bit4)`，配合 `PendingCount` 判断是否存在待裁决专注数据 |
| `0x25 / 0x82` | `OP_BATCH` | 支持补报专注进入、完成、跳过等离线操作 |
| `0x25 / 0x05` | `OP_ACK` | App 确认连续处理成功的最大 `OperationID` |
| `0x14 v2` | `FocusStatus` | 增加会话 ID、版本、状态和权威计时字段 |
| `0x10 v2` | `EnterTaskIn` | 增加 `OperationID`、`FocusSessionId` 和开始时间 |
| `0x11 v2` | `CompleteTask` | 增加操作 ID、会话 ID、结束时间和累计时长 |
| `0x12 v2` | `SkipTask` | 增加操作 ID、会话 ID、结束时间和累计时长 |

Payload 长度：

- `FocusStatus 0x14 v2`：`25+N`。
- `EnterTaskIn 0x10 v2`：`18+N`。
- `CompleteTask 0x11 v2`：`22+N`。
- `SkipTask 0x12 v2`：`22+N`。

### 5. 重连处理顺序

```text
DeviceWake
    ↓
STATE：读取 PendingCount 和 FocusSyncPending
    ↓
FOCUS_STATE：读取设备专注快照
    ↓
OP_BATCH：按 OperationID 顺序回放离线操作
    ↓
OP_ACK：确认连续处理成功的最大 OperationID
    ↓
FOCUS_RESOLVE：下发最终裁决
    ↓
RESULT：设备确认裁决已落地
    ↓
收到匹配的 COMMITTED 后解除锁定
    ↓
恢复普通 FocusStatus、TaskInPage、DayPack、Schedule 同步
```

`OP_ACK` 只能确认连续处理成功的操作。遇到缺口或失败时必须停止推进 ACK，不能越过失败记录确认后续操作。

### 6. DayPack 与 COMMIT 边界

- 专注重连不要求发送 DayPack。
- 普通 `DayPack（Type 0x10）` 只更新业务数据，当前固件不会因为收到普通 DayPack 而退出 TaskIn。
- OfflineSync `COMMIT（Type 0x25 / Opcode 0x02）` 只用于提交 TaskList、Schedule、DayPack 等数据集事务，不能代替专注裁决。
- 为兼容现网旧固件，活动专注期间禁止发送 OfflineSync `COMMIT`，需要提交的数据延后到退出专注后处理。
- TaskIn 是否退出应由同一会话的结束裁决或非 active 的权威 `FocusStatus` 决定，不能由 DayPack 或数据 COMMIT 驱动。

### 7. Schedule 协议升级

`Schedule（Type 0x03）` 升级为 `SubVersion 0x02`，Payload：

```text
SubVersion + Year + Month + Day + EventCount + Events[]
```

每条 Event 固定包含：

```text
Time + Title + Description + Category + EndTime + SupportText
```

主要要求：

- `Description` 必须非空。
- 定时事件的开始和结束时间必须为 `HH:mm`。
- 全天事件的开始、结束时间长度都为 0。
- App 必须发送完整事件，不能继续发送旧版“标题+开始时间”的简化结构。
- Schedule 与 DayPack 的日程字段完全相同时不替换；任一可见字段不同时，由完整 Schedule 原子替换日期和日程。
- 同一离线事务同时包含 DayPack 和 Schedule 时，先应用 DayPack，再应用 Schedule；Schedule 对日程字段拥有最终优先级。
