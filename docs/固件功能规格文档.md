**① 任务/日程各 20 条上限——但只在 App 侧。** App 至多发当天前 20 条任务、最早 20 条日程，超出静默丢弃；**固件规则一个字没变**：收到多少存多少、不自行计数、不自行截断，放不下仍回 `capacityExceeded`。`UpsertCount`/`EventCount` 仍是 4B，只是取值恒 ≤20。两个派生现象**不是 bug**：当天 >20 条时被硬件跳过的任务会掉出前 20 而从设备消失；完成/删除走即时小事务不提拔第 21 条，设备暂时只剩 19 条、最多 180 秒后补齐。（第 22 条 / §8.4 / BLE §4.22、§4.23、§6.8）

**② BLE 常开，省电靠设备侧电源管理与连接参数，不靠断连、也不需要任何自定义帧。**（第 24-A / 24-B 条，**作废 §3.6 的「屏保断开 BLE 省电」**）只用 Modem-sleep + 自动 Light-sleep；开齐 PM 支持 + `configUSE_TICKLESS_IDLE` + Bluetooth Modem sleep Mode 1 + 32.768 kHz 外部晶振（连接保持中约 230 µA）；经 L2CAP 申请「短连接间隔 + 高 Peripheral Latency」。**应用层不得进入「连着但不响应 GATT」的状态**——暂时无法执行的操作用 ATT 应用错误码 `0x80`–`0x9F` 拒绝该次请求。需按新策略重新测算并回报续航。（BLE §2.5）

> ⚠️ **若你看过任何写着 `0x25 DevicePowerControl` 的中间稿，那个帧已整体撤销，不要实现。** 它的前提不成立：设备能应答 GATT 读，本身就证明应用层已经醒着（GATT 回调跑在主 CPU 的 host 栈上）；真睡到应答不了时连接早断了，那帧也发不出去。理由详见 BLE §2.5.3。

## 实施总清单（2026-08-03 · 一页看完）

> 本清单是当前全部改动的**固件视角汇总**，字节级细节以 BLE 协议 **v2.17.0** 为准。v2.10 的 `SupportText` 与 v2.9 任务动作都必须与 App 一次 flag-day 同步切换，旧格式不可混用。
>
> ⚠️ **不要读 v2.15.0**：v2.16.0 的主要内容就是**更正 v2.15.0 §4.22 迁移表的一处错误**（那一版误写「固件停发入站 `0x10 EnterTaskIn`」，照做会让 App 永远不建立专注会话）。本清单**第 25 条**已按 v2.16.0 重写。
>
> **第五组（19–24）与第六组（25–27）是 Issue #26 / #27 / #28 的开工范围**，对应 BLE v2.16.0。这两组**不改任何字节**，改的是设备行为、连接握手顺序、断电恢复与新旧通路切换。两个最容易踩的坑：**第 20 条**（无离线事件也必须回空 `0x21`，不做直接表现为「连上就断」且无错误码）和**第 25 条**（入站 `0x10 EnterTaskIn` **不能停发**——它是唯一的专注开始信号；要改的是发完不再等 `0x11`）。

**一、字节解析（少读一个字节整包错位）**

1. **日程包 DayPack (0x10)**：每条日程在"类别图标"字节后**多读一段结束时间字符串**（"HH:mm"，全天日程为空串），**再多读一段支持性文字**（≤120B，v2.10.0 新增；空串=这行不画）；整包最后**多读两段文字**——总结页"今日点评"（≤180B）和"金句"（≤120B，最后一个字段）。完整字段顺序照 BLE §7.1「当前字段顺序」实现；旧 hex 样例是历史版勿照抄。（BLE §4.7）
2. **宠物状态 PetStatus (0x01)**：末尾**多读 1 字节 CustomActive**（0/1）。（BLE §4.2）
3. **开机上报 DeviceWake (0x30)**：实时 payload 固定 29B：电量 1B + 版本 3B + AvatarState 1B + AvatarID 16B + KRI 长度 4B BE + CRC32 4B BE。无图时后 25B 全填 0。**0x21 批量里的 0x30 记录保持 2B 别动**。（BLE §5.8）

**二、页面逻辑**

4. **早安页**：触发条件 = 今天所有日程都没开始 **且** 还没进过任务；显示满 10 分钟 / 到下一场时间 / 按键，三者任一即切走；用日程的开始/结束时间+类别图标画时间轴。（§3.1）
5. **进行中日程页双布局**：前一场结束到下一场开始**不足 10 分钟** → 完成比例进度条+事件卡；**10 分钟及以上（含恰好）** → 下一场+任务清单。进度条数字直接用 DayPack 里的 TasksCompleted/TasksTotal。（§3.2）
6. **长按 = 完成当日** → 总结页；总结页**再长按 = 返回**（防误触）。总结页 = 两段文字（点评+金句，App 发来）+ 数字区；**没有"明日预告"行**（客户确认取消）。（§3.4）
7. **专注页三阶段**按 0x14 的 Phase 切画面（1=0-5 分钟 / 2=5-15 / 3=15+）；专注进行中 Phase 恒 ≥1；瓶子最多收到 5。任务页原"鼓励语"（Tips）槽位**自 v2.10.0 起改装成支持性文字**（≤80B）——**收到非空就正常画这行，空串仍不画**。注意 Tips 功能本身仍停用、没回来，这一行是新内容、按新语义设计。（§3.3）
8. **屏保**：收到 0x31 睡眠后 App 会回发一帧 0x16 金句——**断连前留接收窗口**（或用缓存金句）；退出屏保**回到进屏保前的页面**。（§3.6）

**三、自定义形象（新逻辑核心）**

9. **0x15 只写候选临时文件**：按 OperationID+AvatarID 从 Seq=0 顺序写入，校验 KRI 头、宽≤800、高≤700、长度和 CRC。通过后回 `0x22 staged`，继续显示旧图；收到匹配 commit 后才原子替换正式文件、启用自定义形象并回 `committed`。（BLE §4.12/§4.19/§5.19）
10. **擦除和恢复**：`eraseExact` 只按 AvatarID 匹配，不按 CRC；匹配时擦除并重建头像分区后才回 `erased`。不匹配表示目标已不在设备上，幂等回 `erased`，同时如实回报未改动的当前库存，绝不能擦错图。`eraseAll` 用于退出登录，总是擦除并重建整个头像分区。query 必须如实回 staged/committed 库存，支持 App 被杀或结果丢失后恢复。显示规则仍是 CustomActive=1 用 committed 用户图，=0 用 CharacterId 内置图；专注页恒用内置美术。
11. **query 只回一个文件**：旧 committed 与新 staged 可以同时存在。若 query 的 OperationID 匹配已校验完成的 staged，就回 staged 的 AvatarID/长度/CRC；否则回 committed，没有 committed 才回 empty。结果 OperationID 永远原样回显本次 query 的 OperationID，不填文件以前的 OperationID。`CustomActive` 始终表示当前实际显示状态，不能因为回了 staged 就改成新图。未收完或未校验的临时文件不算 staged；query 每次重新读取当前库存，不缓存旧结果，也不得修改任何文件。（BLE §4.19/§5.19）

**四、任务完成 / 跳过 / 刷新（v2.9.0 flag-day）**

12. **严格请求格式**：Complete/Skip 固定发 `SubVersion(0x01)+OperationID(4B BE, nonzero)+TaskIdLength+TaskId+Timestamp(4B BE)`；Refresh 固定发 `SubVersion(0x01)+RequestID(4B BE, nonzero)`。空 payload `0x20` 与旧 Complete/Skip 格式全部停发。（BLE §5.4/§5.5/§5.7）
13. **在线任务动作只刷一次**：GATT withResponse 只确认字节传输。Complete/Skip 后保持 TaskIn/pending；先收到的最终 DayPack 只替换后台缓存，**不刷屏、不退出**。只有随后收到 Action+OperationID 匹配且版本更新的 `TaskListSnapshotAck(0x1B)`，才能把缓存和 Overview 清单一次提交并刷新一次。Complete 的快照移除任务；Skip 只结束专注，任务保留。RequestRefresh 仍立即处理 `0x1B`。（BLE §4.21）
14. **幂等重试**：丢失 `0x1B` 时原样重发相同 Action/OperationID/TaskId/Timestamp。不得生成新 ID、不得修改时间戳。App 用持久账本去重；同 ID 不同 payload 返回 invalidRequest。（BLE §8.4）
15. **离线迁移**：`0x11/0x12` 可进入 EventLogBatch，但记录必须是 v1；`0x20` 只走实时 Notify，禁止入批次。升级 v2.9.0 时清空含旧格式记录的环形缓冲，避免新解析器整批拒绝。（BLE §5.15）
16. **App 新状态优先**：收到 `supersededByApp(0x04)` 表示 App 的更新操作或更新专注会话已获胜。固件结束该 pending、采用同帧完整快照，不再重试旧动作。（BLE §4.21）
17. **短按不死等**（**仅适用迁移 A 阶段**）：任务短按时，没有活跃 BLE 连接就直接按本地状态机进入可用页面/交互；有连接才等 App 的 `TaskInPage(0x11)`，最多 5 秒。超时后本地兜底或回 Overview/Interactive，保留事件供重连后有限重试。设备本地结果不是 App 的最终任务提交。（BLE §5.3）
    > ⚠️ **切到 B 阶段后本条整条作废**：短按不再发入站 `0x10`、不再等 `0x11`，而是**直接读本地已提交任务库**并立刻进入专注页（无等待、无超时、离线在线行为一致）。见第 25 条与 BLE §4.22「迁移与切换阶段」。
18. **DayPack 只留最后一份**：当前日程的开始/结束边界由 RTC 本地切换页面。EPD 正在刷新时收到多个 DayPack，覆盖待渲染缓存，当前刷新结束后最多再刷一次。App 自动同步可能因只有对话、`FirstUp` 或统计变化而不发 DayPack，这是正常；任务、日程、`SupportText` 和最终任务动作仍会收到更新。（BLE §8.3/§8.5）

**五、断联专注与离线动作（v2.14.0 新增，wire 不变、行为变）**

19. **断连不结束专注**：BLE 断开时**保持当前专注页**，按本地 RTC 继续计时，并按 `0–5 / 6–15 / 16+` 分钟边界**本地切换**三阶段文案（文案来自已提交任务库，断连期间不得向 App 索取）。重连**不回概览、不新建会话、不清零时长**，并恢复 §5.7 的 ~5 分钟周期 `0x20`。**v1.8.0–v1.9.2 的「断连即会话结束 → 退回概览」作废。**（BLE §9.6）
20. **⚠️ 每次 `0x20 EventLogRequest` 必回一帧 `0x21`——没有离线事件也要回空批次。** App 在安全握手后立即发本帧，并在处理完对应 `0x21` 之前**不下发任何显示数据**；**15 秒**未完成即判本次连接失败并主动断开。不回 = 「连上就断、反复重连、收不到任何内容」且**没有任何错误码**。这是本版最容易踩的坑。（BLE §4.13 / §5.23）
21. **离线动作先本地生效并持久化**：断连期间短按完成 / 长按跳过，设备**立即本地执行**（更新任务库、更新队列、返回来源页面），不进待确认态、不禁用按键。同时写一条记录，含**非零 OperationID**、TaskId、Timestamp，并保留**原始发生顺序**（不得按 RTC 重排）。记录须**跨断电与重启持久化**；未收到匹配 `0x1B` 的动作重启后继续回放，重发时**原样复用**同一 OperationID 与 payload 字节。（BLE §5.23）
22. **顺序任务队列**：任务库内容 = **当天任务**（dueDate 当天 ∪ 手动设为今天，08-04 修订——由 App 筛选，固件照单全收、不自行按日期过滤）。短按**只进队首**；完成 → 移出任务库、下一项成为队首；跳过 → 移到**队尾**、任务保留、**不发能量瓶**。**不做滚轮、高亮或任意任务选择**，App 是调序唯一入口。**显示条数与保存条数分离**——屏幕一次显示几项不得反过来截断任务库，固件**不自行**设置八项或其他任意上限（真放不下时整次事务失败回 `capacityExceeded`，不许截断后报成功）。**条数上限是 App 的职责**：v2.17.0 起 App 至多发当天前 20 条，所以你收到的 `UpsertCount` 恒 ≤20——但固件规则不变，收到多少存多少、不自行计数、不自行截断。当天 >20 条时被跳过的任务会被 App 移出前 20 而从设备消失（「队尾」即第 21 位），这是预期行为不是 bug。（BLE §6.8 / §5.21 / §4.22）
23. **来源页面返回**：进入专注、每日总结、屏保前记录来源页面，退出时**返回该页面**而不是固定跳概览（总结当前来源是页面二，再长按即回页面二）。来源页面是设备本地状态，不经 wire、不被任何 App 帧改写。墨水屏只做**静态刷新**：无声音、无震动、无完成动画（本条不约束 iPhone 端）。（BLE §6.8）
24. **冲突合并四条固定优先级**（重连回放后 App 侧执行，固件据此理解结果）：完成 **>** 内容编辑；跳过与内容编辑**并存**（最新内容 + 队尾）；删除 **>** 跳过；先取 App 最新顺序为基础、再按离线跳过先后依次移队尾。断联专注的任务被删除时**重连不打断当前专注**，用户完成后专注时长与能量**照常结算**但任务**不恢复**。（BLE §8.8）

**五之二、BLE 常开与设备低功耗（v2.17.0 新增，不新增帧）**

24-A. **BLE 常开**：设备进入屏保或低功耗后，**广播与已建立的连接必须保持可达**。**v1.9.2–v1.12.0 的「进入屏保后断开 BLE 省电」（§3.6）作废。**（BLE §2.5）

24-B. **省电靠电源管理配置，不靠断连、也不靠自定义帧。** ⚠️ **中间稿里的 `0x25 DevicePowerControl` 已撤销，不要实现。** 改为：

    - **不得进入会断连的睡眠**：deep sleep 与手动 light sleep 都会掉射频、断开连接（deep sleep 唤醒等同重启）。**唯一可用的是 Modem-sleep + 自动 Light-sleep**——该模式下 controller 按连接事件调度自动唤醒系统，上下文完整保留、醒来从原地继续。
    - **必须开齐这几项**，否则蓝牙会持有 `ESP_PM_NO_LIGHT_SLEEP` 锁、设备进不了光睡眠：电源管理（PM）支持、`configUSE_TICKLESS_IDLE`、Bluetooth Modem sleep **Mode 1**、light sleep 期间按需开启主晶振、**32.768 kHz 外部晶振**（用内部 RC 会因时钟精度不足掉线；136 kHz RC 振荡器**不支持连接**）。达成后连接保持中约 **230 µA**（Modem sleep 单独约 17.9 mA）。
    - **经 L2CAP Connection Parameter Update Request 申请省电参数**：Peripheral Latency 允许连续跳过 N 个连接事件不应答，协议明确许可、不触发 supervision timeout，有数据时下一个事件即可响应。申请值必须满足 Apple 的六条约束（BLE §2.5.2 列出），推荐 Interval 15–30 ms / Latency 20 / Supervision 6000 ms。大数据量传输（`0x15` 头像、多分片 `0x23`/`0x24`）期间可临时申请更激进参数，传完再申请回省电档。
    - **应用层不得进入「连着但不响应 GATT」的状态。** 墨水屏保持画面本身不耗电，没有理由为省电拆掉业务状态机。暂时无法执行的操作（如 EPD 正在刷新）用 **ATT 应用错误码 `0x80`–`0x9F`** 拒绝该次请求，App 会退避重试。（BLE §2.5）

**六、迁移、断电恢复与交付（v2.15.0 新增，wire 不变）**

25. **迁移阶段：入站 `0x10 EnterTaskIn` 照发不误，改的是不再等 `0x11`。**
    ⚠️⚠️ **`0x10 EnterTaskIn` 不能停发**——它是 Device→App **唯一**的「专注已开始」信号。停发会让 App 永远不建立专注会话：**能量瓶不计、打断检测不启动、`0x14 FocusStatus` 不再下发、专注记录全丢**。
    ⚠️ 方向双义：`0x10` **出站 = DayPack**、**入站 = EnterTaskIn**；**出站 DayPack 别动**（由 `0x24` 另行接管）。
    **本次真正要改的**：进任务时**照发入站 `0x10`**，随后**立即**从本地已提交任务库读标题、详情和三阶段文案进入专注页——**不等 `0x11`、不设超时**，收到 `0x11` 也忽略。**App 已经不再回发 `0x11`（Issue #29 已落地）。**
    **过渡期（固件尚未改完）**：App 不回 `0x11`，固件靠 §5.3 的 **5 秒超时 → 本地兜底**降级，用户表现为进任务慢 5 秒。**⚠️ 请优先确认这条超时确实已实现**——没实现就会卡在等待页，这是本次 App 先行唯一的真实风险。
    **任务库缺失时**显示空任务列表 + 本地默认对话并按 §5.8 报 missing，**禁止回落索取现场详情**（App 侧路径已删，索取不会有应答）。`0x1B` 一直生效，**不在删除范围**。（BLE §4.22「迁移与切换阶段」）
26. **设备侧断电恢复**：任务库 / 当天内容包 / 离线动作三者**各自独立**持久化；**版本标识与内容必须一起原子落盘**（禁止「版本已推进但内容是旧的」——App 会据设备上报版本跳过全量重发，从此永久停在错误内容上）；暂存区与 committed 区**物理分离**，未通过校验的暂存断电后**绝不能**成为当前版本；重启读最后一份 committed，没有就如实报 missing。**「提交完成但应答未发出」时 App 会用同一 Epoch/Revision/CRC 整包重发——设备发现与当前 committed 完全一致时应幂等直接回 `committed`，不必也不应重新擦写 flash。** 完整掉电矩阵见 BLE §8.9。
27. **交付证据**：每个 Issue 交付时按 **§8.5** 提交固件版本、对齐的协议版本、构建结果、设备型号、串口关键状态证据和逐条场景结果；**证据强制脱敏**——不得含用户原始任务/日程文字，不得含 `BLE_SHARED_SECRET`、API key 或任何凭据。Swift 仿真通过**不能**替代设备端证据。

## 1. 产品概述

### 1.1 产品定位

**Unlock the Flow, Make it Happen.**

Kirole 是一款面向深度知识工具用户的专注力伴侣设备。它把 iOS App 中的任务、日程、智能提醒、专注状态和三位 IP 伴侣同步到 E-ink 屏幕，帮助用户在低干扰界面里看到今天要做什么、现在该关注什么。

### 1.2 核心功能

| 功能 | 描述 |
|------|------|
| 伴侣陪伴 | Joy / Silas / Nova 三位 IP 伴侣提供短句陪伴和情绪反馈 |
| 专注反馈 | 反映用户专注模式和注意力数据，量化专注时间与中断次数 |
| 智能提醒 | 基于行为模式的上下文感知提醒，在合适时机推送到设备 |
| 任务展示 | 显示今日任务列表，支持完成标记 |
| 场景解锁 | 通过专注获得能量瓶，逐步解锁 harbor / forest / nightCity |
| 日程提醒 | 展示日历事件和时间安排 |
| 每日结算 | 统计当日完成情况，含专注指标和积分奖励 |

### 1.3 产品形态

- **设备类型:** 展示型 E-ink 设备
- **尺寸规格:** 4寸 / 7.3寸 两种规格
- **交互方式:** 电源键 + 旋钮按键 + BLE 连接 iOS App
- **供电方式:** 内置电池 + USB-C 充电

### 1.4 目标用户

- 深度知识工具用户（使用多种生产力工具但执行力不足）
- 远程工作者
- 自由职业者
- 需要专注力管理的用户
- 喜欢像素风格/电子宠物的用户

## 3. 显示页面设计

设备共有 4 个主要页面，通过时段自动切换或用户手动操作切换。**各页面的视觉布局/示意图以硬件团队的实际 UI 设计为准，本文档不再附 ASCII 示意图**；字段语义、触发与交互说明仍保留。

### 3.1 Page 1: Start of Day (早安页 / 每日开始日程概览)

**触发（v1.6.0，客户《电子墨水屏需求》调整）:** 两个条件**同时满足**时显示：
1. 日程表**全部日程未到达开始时间**（本地 RTC 对比 `Events[]` 各条 `Time`）；
2. **当日尚未进入过任务**（判定信号：本地未发过 `EnterTaskIn(0x10)`，且未收到过 Phase≠0 的 `0x14 FocusStatus`——App 侧发起的专注也计入「已进入任务」）。

开机默认显示行为保留（开机时以上两条件通常天然成立）。

**退出（三选一，先到先触发）:**
- 显示满 **10 分钟**自动切换 → Overview；
- **到达下一个日程的开始时间** → Overview；
- 任意按键 → Overview。

**数据字段:**

Page 1 与 Page 2 同属 `DayPack(0x10)`（见 §3.2 + BLE通信协议规格文档 §4.7）。一天开始页用到：`PetDialogue`（晨安气泡，单句）、`DaySummary`（一天总结，框②，**中性**面板文案——v2.5.30 起规则：日程繁忙/紧凑给休息建议，空闲则提醒喝水）、`FirstUp`（下一项，框③）、天气（`Weather 0x04`，含高/低温）。**旧字段 `morningGreeting / dailySummary / firstItem` 已于 v2.5.0 删除/更名，勿照其实现。**

**日程概览时间轴（v1.6.0 新增，固件渲染）:** 在 `DaySummary` 框下方绘制一条**横向时间轴**，把今日日程以**类别图标**打标在对应时间位置：
- 图标 = `Events[]` 每条的 `Category` 字节选择固件内置六类图标（BLE §4.7 Category 表，资产 `docs/assets/event-category-icons/`）；
- 位置 = 各条 `Time`（起始时间）在时间轴上的投影；相邻/重叠时段的图标可聚簇堆叠（参考客户示意图）；
- 端点 = 左太阳 / 右月亮（固件内置装饰图标）；首尾事件下方标注其时刻（如 "7:00" / "17:30"，来自 `Time`/`EndTime`）；
- 数据全部来自现有 DayPack 字段，**App 不为时间轴新增字段**。

### 3.2 Page 2: Overview (概览页)

> **重要（v2.5.0+，本节模型已更新）**：Page 1（一天开始）与 Page 2（概览）由**同一个 `DayPack(0x10)` 帧**驱动，不是各自独立的帧/字段。设备 UI **不是旧的「混合时间线」**（日程+任务交织成一条列表），而是「**常驻宠物气泡 + 可换数据面板**」：宠物口吻只有一句气泡 `PetDialogue`，其余皆为结构化面板数据（**事件卡、任务表分块，非混合**）。**权威字段与布局以 BLE通信协议规格文档 §4.7（DayPack）+ §6 / §6.5 为准**；下方旧 ASCII 示意与字段名仅作历史参考。

**面板构成（按设计稿渲染，详见 BLE §4.7 / §6.5）:**
- 顶栏: 天气（`Weather 0x04`，含高/低温）+ 日期。
- 宠物气泡: `PetDialogue`（单句，阶段感知）。
- 一天总结（框②）: `DaySummary`（**中性**面板文案，非宠物口吻；只谈日程 + 一条实用建议）。
- 下一项（框③）: `FirstUp`（下一个未来事件「HH:mm 标题」，无则置顶任务标题；App 算好下发）。
- 事件卡: `Events[]`（时间 / 标题 / 描述），按时间、只读。
- 任务表: `TopTasks[]`（标题 / 完成态 / 优先级），**按优先级排序**，可选进 Task In。
- 进度 / 能量: 来自 `SettlementData` 数值（完成 / 总数、积分、专注指标、能量瓶）。

> **v1.8.0 当前任务清单来源**：启动/常规同步时从 DayPack.`TopTasks[]` 取得；完成、跳过或刷新后，以匹配且版本更新的 `TaskListSnapshotAck(0x1B).Tasks[]` **原子替换**任务区域。两者使用相同筛选：只含当天未完成任务，4 寸最多 3 项、7.3 寸最多 5 项。`TaskList(0x02)` 是 legacy，不能作为新状态机的数据源。

> **双布局拍板（v1.6.0，客户《电子墨水屏需求》，替代旧「进度条 vs 任务清单」开放问题）**：概览页按**相邻日程间隔**在固件本地二分——取「前一个日程的 `EndTime` 到下一个日程的 `Time`」（"HH:mm" 本地转分钟比较，`EndTime` 为 BLE v2.5.30 新增字段）：
> - **情况一（间隔 <10 分钟）**：显示**当日日程完成情况比例**（进度条，`SettlementData.TasksCompleted/TasksTotal`，如 "●●●●●○○○○○ 50%"）+ 事件卡（`Events[]`）；
> - **情况二（间隔 ≥10 分钟）**：显示下一个日程的事件卡 + **任务清单**（`TopTasks[]`，"Task List" bullet 布局）。**恰好 10 分钟归情况二**（客户确认默认口径，2026-07-20，v1.6.0）。
>
> 判定在固件本地做，App 两组数据都发、**不引入 PanelMode 字节**（BLE v2.5.15 拍板不变，判定优先级表见 **BLE §6.7**：专注中→态 C 等）。「任务前三按 AI 排序」仍是**待客户确认项（暂缓）**，当前 App 按优先级排。

**显示时机:** 从 Start of Day 达到切换条件（10 分钟 / 到点 / 按键，见 §3.1）进入；或从专注任务页短按/长按退出后回到本页

**排序规则:**
- 日程: 按时间排序，仅显示不可交互
- 任务: 按优先级排序，可选择进入 Task In

**显示数量:** 根据屏幕尺寸调整 (4寸/7寸不同)
**空状态:** 显示"今日无任务"提示

**交互:**
- 滚轮滚动: 选择项目 (反色高亮)
- 按下滚轮/短按 (任务): 无活跃 BLE 时直接按本地状态机进入可用交互；有 BLE 时发送 `EnterTaskIn(0x10)` 并最多等待 App 回发 `TaskInPage(0x11)` 5 秒。超时走本地兜底或回 Overview/Interactive，保留事件供后续同步，不能无限等待
- 按下滚轮 (日程): 显示日程详情 (自动超时返回)
- **长按 (>1s)（v1.6.0 新增）: 「完成当日」→ 进入每日总结页（§3.4）**。与 Task In 页「长按=跳过任务」是**不同页面语境**，不冲突；误触保护见 §3.4

**数据字段:** 见 `DayPack(0x10)`，BLE通信协议规格文档 §4.7（`PetDialogue` / `Events[]`（每条含 `Time`/`EndTime`/`Category`/`SupportText`）/ `TopTasks[]` / `SettlementData` / `DaySummary` / `FirstUp` / `SettlementReview` / `SettlementQuote`，后两者为 v2.5.30/v2.5.31 每日总结页文案）。`SupportText` 为 v2.10.0 每条日程的支持性文字（该日程进行中时显示，≤120B，**排版位置固件自行决定**，空串不渲染）。**旧字段 `currentScheduleSummary / mixedTimeline / companionPhrase` 已于 v2.5.0 删除，勿照其实现。**

### 3.3 Page 3: Task In (任务详情页)

**显示时机:** 从 Overview 选择任务进入


**触发:** 从 Overview 选择任务进入
**交互:**
- 短按滚轮: 发送 CompleteTask v1，保持 TaskIn/pending；先缓存最终 DayPack，收到匹配 `0x1B` 后一次返回 Overview 并刷新
- 长按滚轮 (>1s): 发送 SkipTask v1，保持 TaskIn/pending；先缓存最终 DayPack，收到匹配 `0x1B` 后一次返回 Overview 并刷新，任务仍保留

**事件同步（v1.8.0）:**
- 进入任务时: 发送 `EnterTaskIn` 事件 (带时间戳)
- 完成任务时: 发送严格 v1 `CompleteTask`（非零 OperationID + TaskId + Timestamp）
- 跳过任务时: 发送严格 v1 `SkipTask`（非零 OperationID + TaskId + Timestamp）
- 等待期间可显示 pending，但不得永久删除本地任务；超时必须原样重发同一请求
- 只有 Action+OperationID 匹配且 StateEpoch/Revision 更新的 `0x1B` 才能原子替换 Overview 清单。Complete 后任务移除；Skip 后任务保留（当前选择允许随 App 排序变化）

**数据字段:**

> **⚠️ 下表字段不再由 `0x11 TaskInPage` 下发，改为从已提交任务库（`0x23`，BLE §4.22）本地读取。**
> App 自 Issue #29 起已删除 `0x11` 的生成与发送路径——**等它只会等到 §5.3 的 5 秒超时**。
> 进任务时仍照发入站 `0x10 EnterTaskIn`（专注开始通知，不可停发），发完**立即**用本地任务库的
> `Title` / `Detail` / 三阶段文案渲染专注页。下表保留是为了给出字段语义与长度，**不再代表一个到达的帧**。
> 三阶段文案按本地专注分钟在 `0–5 / 6–15 / 16+` 之间自行切换（BLE §9.6），不向 App 索取。

| 字段 | 最大长度 | 描述 |
|------|----------|------|
| taskTitle | 40 字符 | 任务标题（现由 `0x23` 任务记录的 `Title` 提供） |
| taskDescription | 100 字符 | 任务描述 (可选，"Overview" 段)（现由 `0x23` 任务记录的 `Detail` 提供） |
| encouragement | 80 字节 | **支持性文字**（改由 `0x23` 任务记录的三阶段文案提供，按本地专注分钟选段；占用原"*Tips"段的槽位）。**v1.9.0 改装**：App 按 **Deep Work** 规则生成一句话——只指向最小的第一步、不展示任务全貌；上限 50→**80 字节**。收到非空即渲染，空串（生成与兜底都失败的极端情况）仍不渲染该行。⚠️ 原 Tips 功能仍停用（客户 2026-07-20，未推翻），此槽位语义已换、勿套用旧 Tips 的渲染设计 |
| focusChallengeActive | 1 byte | 专注挑战状态 |

**三阶段画面（v1.6.0，客户《电子墨水屏需求》页面三）:** 专注页按已专注时长逐步切换三套画面（美术为固件内置，宠物姿态/瓶子填充渐进变化）：

| 阶段 | 时长 | 数据信号 |
|------|------|----------|
| 阶段一 | 0-5 分钟 | `0x14 FocusStatus` Phase=1 (warmup) |
| 阶段二 | 5-15 分钟 | Phase=2 (building) |
| 阶段三 | >15 分钟 | Phase=3 (deep) |

阶段以 `0x14` 的 `Phase` 字节为准（按**当前未打断段**计，打断退回 warmup，见 BLE §4.11）；**会话活跃时 Phase 恒 ≥1**（App v2.5.31 起第 0 分钟/打断清零瞬间也发 warmup，`Phase=0` 只表示无会话）；能量瓶子随 `Bottles` 字段逐步增多（App 侧显示封顶 5，v2.5.29）。

> **自定义 IP 在专注页（v1.6.0）**：自定义形象激活时，专注页**仍用内置 IP 美术**（按最近一次 `0x01 CharacterId`）——用户单图无三阶段姿态，多图上传暂不支持（客户 2026-07-20 确认现状；其余页面见 §5.1 口径）。

### 3.6 屏保模式

**触发:** 按电源键
**内容:** 静态伴侣场景图（桌面装饰，满屏 1600×1200，底图**无文字**）+ **金句文本叠加层**
**金句:** 由 App 生成、经 BLE 推送的**动态文本**（如励志引文 + 作者），固件运行时叠加绘制在屏保图上（建议绘制区＝画面上半中部）。屏保底图本身不含任何文字。
- **帧已升级为业务帧（v2.5.10）**：金句经 **`0x16` Screensaver 业务帧** 下发（payload 字段 `ContentType / SceneByte / PostcardDay / QuoteLen+Quote / AuthorLen+Author`，见 BLE 通信协议规格文档 **§4.15**）。App 端已实现金句**生成**（`ScreensaverService.getScreensaverConfig` / `OpenAIService.generateScreensaverQuote`，引文 <60 字符）与**封帧下发**（`BLEDataEncoder.encodeScreensaver` → `BLEService.sendScreensaverConfig`，经 `writeData`）。
- ⚠️ **发送路径（固件须知）**：
  1. **被动触发、且依赖此刻仍连接**：App 不主动定时推送金句，而是在收到硬件 sleep 事件（`handleHardwareSleep`）后即时下发。若固件进入屏保后**立刻断连**，这帧可能来不及送达——固件应在断连前预留收帧窗口，或缓存上一次金句。
  2. ~~secure mode 下被拒~~ **已解决（v2.5.10）**：金句已从旧 `0xAA 01 02` 开发命令升级为 `0x16` 业务帧、改走 `writeData`——**dev / secure（生产签名通道）两种模式均可发**（secure 下自动经 SecureEnvelope 封装）。原「仅开发/未签名模式可达」的限制不再存在。
- ⚠️ **渲染侧（固件待实现）**：**固件需正式支持 `0x16` Screensaver 业务帧并渲染 Quote/Author**（按 BLE 协议 §4.15 的 payload 布局解析）。这是标准业务帧、不再是可忽略的 `0xAA` 开发命令。屏保帧**可能单包亦可能分包**（Quote/Author 长或 secure 封装后超 MTU），固件须按 §3.2 通用分包重组、不可假设恒为单包。
- ⚠️ **场景底图经 `0x17` SceneUnlock 切换（固件待实现）**：屏保叠加金句的**底图**（harbor/forest/nightCity）由 App 经 `0x17` SceneUnlock 业务帧推送/切换（payload = 1B SceneId：`0x00=harbor / 0x01=forest / 0x02=nightCity`，恒为单包，见 BLE 协议 §4.16）。旧 `0xAA 01 01` 场景命令已废弃；注意 `0x17` 出站=SceneUnlock、入站=ReminderDismissed（方向分离）。
**BLE:** ~~进入屏保后断开连接（省电）~~ **⚠️ 本条已由 BLE v2.17.0 作废（2026-08-04 客户拍板）：硬件 BLE 常开**——进入屏保后必须保持广播与已建立连接可达，App 才能在设备低功耗时正常连上并同步（BLE §2.5）。金句仍应在收到 `0x31 DeviceSleep` 后的窗口内接收并缓存，但不再依赖「断连前送达」这个前提。**续航影响需重新评估**：§2.6 的待机承诺（4寸 ~30 天 / 7寸 ~20 天）是按屏保断连测算的。
**退出（v1.6.0 调整）:** 再次短按电源键 → **切回进入屏保前的页面**（客户《电子墨水屏需求》页面四「跳出条件：再次短按电源键，切回原界面」；原「返回 Start of Day」废弃）

## 6. 数据同步

### 6.1 BLE 协议概要

第一次硬件联调请先参考 `BLE初次联调指南.md`。完整协议请参考 `BLE通信协议规格文档.md`。

BLE `Type` 字节必须按方向解释。同一个 `Type` 在 App→Device 和 Device→App 中可以有不同含义，固件不能只按 `Type` 判断业务。

#### 主要命令

| 命令 | 类型码 | 方向 | 描述 |
|------|--------|------|------|
| DayPack | 0x10 | App → Device | 发送每日数据包 |
| TaskInPage | 0x11 | App → Device | 发送任务详情 |
| DeviceMode | 0x12 | App → Device | 设置设备模式 |
| SmartReminder | 0x13 | App → Device | AI 智能提醒推送 |
| FocusStatus | 0x14 | App → Device | 推送当前专注阶段、会话能量瓶子数、已专注分钟数和任务标题 |
| TaskListSnapshotAck | 0x1B | App → Device | 任务动作/刷新业务确认 + 当前完整 Overview 清单 |
| EventLogRequest | 0x20 | App → Device | 请求指定时间戳之后的事件日志 |
| DeviceWake | 0x30 | Device → App | 设备唤醒并上报电量 |
| EnterTaskIn | 0x10 | Device → App | 进入任务详情，触发 App 回发 TaskInPage |
| CompleteTask | 0x11 | Device → App | v1 任务完成请求（非零 OperationID） |
| SkipTask | 0x12 | Device → App | v1 跳过请求（非零 OperationID） |
| WheelSelect | 0x14 | Device → App | 滚轮选择确认 (发送选中项 ID；App 当前仅记录/调试，不回发详情) |
| ViewEventDetail | 0x15 | Device → App | 查看日程详情 |
| ReminderAcknowledged | 0x16 | Device → App | 用户确认收到提醒 |
| ReminderDismissed | 0x17 | Device → App | 提醒超时自动关闭 |
| RequestRefresh | 0x20 | Device → App | v1 请求当前任务快照（非零 RequestID） |
| EventLogBatch | 0x21 | Device → App | 批量回传事件日志 |
| LowBattery | 0x40 | Device → App | 低电量通知 |

> 说明：`0x10`、`0x11`、`0x12`、`0x13`、`0x14`、`0x20`、`0x21` 都可能按方向复用。例如 App→Device 的 `0x14` 是 `FocusStatus`，Device→App 的 `0x14` 是 `WheelSelect`。固件需按链路方向区分解析。`0x1B` 当前只定义 App→Device。

### 6.2 事件发送时机

| 触发条件 | 发送事件 |
|----------|----------|
| 滚轮滚动 | 纯本地处理，不发送事件 |
| 按下确认并进入任务详情 | EnterTaskIn (发送 TaskId + 时间戳；App 回发 TaskInPage) |
| 普通确认但不进入任务详情 | WheelSelect (发送选中项 ID；App 当前仅记录/调试，不回发详情) |
| 按下确认 (日程) | ViewEventDetail |
| 完成任务 | CompleteTask v1：SubVersion + 非零 OperationID + TaskId + Timestamp；保持 pending，依次等待最终 0x10 和匹配 0x1B |
| 跳过任务 | SkipTask v1：SubVersion + 非零 OperationID + TaskId + Timestamp；保持 pending，依次等待最终 0x10 和匹配 0x1B |
| 设备唤醒 | DeviceWake (发送 BatteryLevel) |
| 用户手动刷新 | RequestRefresh v1：SubVersion + 非零 RequestID；等待匹配 0x1B |
| 用户按键关闭提醒 | ReminderAcknowledged (0x16) |
| 提醒 10 秒超时 | ReminderDismissed (0x17) |
| 电量低于 20% | LowBattery |

第一轮联调中，任务详情页可以暂不实现；如果暂不实现，不要用 `WheelSelect` 代替 `EnterTaskIn`，否则 App 不会回发 TaskInPage。

### 6.3 数据刷新时机

| 触发条件 | 刷新内容 |
|----------|----------|
| App 启动 | 完整 DayPack |
| 设备连接 | 完整 DayPack |
| 在线任务完成/跳过 | 先缓存最终 `0x10`（不刷新），再以同版本 `0x1B` 一次提交任务清单和页面刷新 |
| 设备 `RequestRefresh` | 立即 `0x1B` 当前任务清单；这是设备触发的自动仲裁范围，完整 DayPack 仍受 60 秒 full-sync 合并窗、指纹去重和当前日程展示字段仲裁影响。只变对话/`FirstUp`/统计而没有 DayPack 属正常，不能当作 App 未响应 |
| App 侧明确手动同步 | 内容指纹变化时正常下发 DayPack，不受当前日程展示字段仲裁拦截 |
| 定时刷新 (每小时) | 完整 DayPack |

### 6.4 初次联调范围

第一次实验室联调分两道门。第一道先验证 BLE 基础收发：

- 广播 `FFE0` Service UUID。
- 提供 `FFE1` Write 和 `FFE2` Notify。
- 发送 `DeviceWake(0x30)` 上报电量。
- 接收并打印 `Time(0x05)`。
- 发送严格 v1 `RequestRefresh(0x20)`（`01 + RequestID(4B BE, nonzero)`）。
- 接收并解析匹配的 `TaskListSnapshotAck(0x1B)`，校验版本并原子替换任务清单。
- 按内容变化接收并重组 `DayPack(0x10)`，先打印字段，不要求完整 UI 渲染。

第二道在 v2.10.2 双端发布前必须验证：发送真实 TaskId 的 Complete/Skip v1、最终 `0x10 → 0x1B` 只触发一次刷新、匹配 `0x1B` 的移除/保留行为、原样重试返回首次缓存的 Result、冲突 ID invalidRequest、epoch/revision 顺序和旧离线缓冲清理；再验证无 BLE 短按立即可用、有 BLE 但 5 秒不回 `TaskInPage` 时不死等，以及日程边界的展示字段变化不触发第二次全刷。详情步骤以 `BLE初次联调指南.md` v0.2.3 为准；无需先完成 Task In 页视觉渲染，可以用协议测试入口构造动作帧。

第一次联调暂不验收：

- 安全握手和 `SecureData(0x7E)`。
- `EventLogBatch(0x21)` 离线补传。
- `TaskInPage(0x11)` 的完整详情页视觉渲染（不影响用协议入口验收 Complete/Skip）。
- `FocusStatus(0x14)` 专注实时状态。
- `SmartReminder(0x13)`。
- Spectra 6 图片帧传输。

### 6.5 离线行为

| 场景 | 设备行为 |
|------|----------|
| 未连接 App | 显示最后一个**已确认**快照；本地动作可显示 pending |
| 按键完成/跳过任务 | **先本地生效**（更新任务库与顺序队列、返回来源页面），同时写入 v1 离线事件；重连后按**原始发生顺序**原样补传 |
| 专注中断开 BLE | **保持专注页**，按本地 RTC 继续计时并本地切换三阶段文案；**不结束会话、不回概览**（BLE §9.6） |
| 重连 | **不切页、不重建会话、不清零时长**；先回放离线动作，再接受 App 下发内容（BLE §5.23） |
| 跨日未同步 | App 推送新一天内容包 `0x24` **与按新日重算的任务库 `0x23`**（08-04 修订；到达前继续用旧 committed 库） |

`CompleteTask(0x11)` / `SkipTask(0x12)` 可持久化到 `EventLogBatch(0x21)`，但必须保存完整 v1 payload 和稳定 OperationID。`RequestRefresh(0x20)` 是实时控制，不写入环形缓冲。v2.9.0 升级迁移必须清空旧格式 `0x11/0x12/0x20` 记录。

**强制握手（BLE §4.13 / §5.23）：** App 在每次连接的安全握手完成后立即发一帧 `0x20 EventLogRequest`，并在收到并处理完对应 `0x21 EventLogBatch` 之前**不下发任何显示数据**；**15 秒**未完成即判本次连接失败并主动断开。

> ⚠️ **没有离线事件时，固件也必须回一帧空 `0x21`。** 不回不会产生任何错误码，只会表现为「连上就断、反复重连、永远收不到内容」。

离线记录须**跨断电与重启持久化**：尚未收到匹配 `0x1B` 的动作，重启后仍要继续回放，且**原样复用**同一 OperationID 与 payload 字节（同 ID 不同 payload 会被 App 判 `invalidRequest`）。App 侧幂等身份 = （设备 + Action + OperationID），载荷比对用 **wire 上的原始 TaskId 字节**，因此任务行已被移除后重发仍能匹配首次结果，不会重复执行。

### 6.6 任务快照状态机（v1.8.0 / BLE v2.9.0）

`TaskListSnapshotAck(0x1B)` payload：

```text
SubVersion(0x01) | Action(0x11/0x12/0x20) | OperationID(4B BE) |
Result(1B) | StateEpoch(4B BE) | Revision(4B BE) | TaskCount(1B) | Tasks[]
```

Result：`0x00=applied`、`0x01=alreadyApplied`、`0x02=taskNotFound`、`0x03=invalidRequest`、`0x04=supersededByApp`、`0xFF=internalError`。每条 Task 为 `TaskId LP≤36 + Title LP≤30 + IsCompleted(1) + Priority(1)`，其中 LP 表示 `Length(1B)+UTF-8 bytes`；完整字节表见 BLE §4.21。TaskId 是 App 下发的稳定硬件 ID，可能是 `h-` 开头的摘要；固件只保存并原样回传，不按外部平台 ID 或 UUID 规则加工。

固件必须维护：

- 前台当前 pending 请求，以及离线补传队列中每个待确认请求：Action、OperationID、TaskId、Timestamp 和重试计时；OperationID 在「当前设备 + Action」范围内非零。
- 一个已应用版本：`StateEpoch + Revision`。
- 一份最后已确认的 Overview 任务清单。

接收顺序：

1. 先完整解析 `0x1B`，校验所有长度、TaskCount 和 payload 末尾。
2. Action 或 OperationID 与 pending 不匹配：丢弃，不动页面、不结束 pending。
3. StateEpoch 改变：只接受新 epoch 的 `Revision=1`；同 epoch 只接受严格更大的 Revision。
4. 对 `applied/alreadyApplied/taskNotFound/invalidRequest/supersededByApp`，一次性原子替换整个 Overview 清单并结束 pending；错误/冲突结果不得保留设备自行删除的任务。`supersededByApp` 表示 App 新状态优先，禁止继续重试旧动作。`internalError` 才保留最后已确认清单并原样重试请求。
5. 更新选择：若旧选中 TaskId 仍存在则保留；不存在则按新列表选择首项或进入空态。Skip 后任务通常仍存在，但 App 排序变化可以改变当前项。
6. DayPack 与 `0x1B` 都必须等整条简单消息或全部分片重组、校验完成后再应用。不得按分片局部改任务清单；App 保证两类完整消息不交错。
7. App 对同一 revision 的 GATT 短重试会发送完全相同的 `0x1B` 字节。固件收到相同 revision 时保持当前状态即可，不得把它解释成一份新快照。
8. 固件必须把已应用的 `StateEpoch + Revision` 与完整 Overview 清单一起原子落盘；断电后不能出现版本已推进但任务表仍是旧值。

任务清单只含当天未完成任务，4 寸最多 3 项、7.3 寸最多 5 项。DayPack.TopTasks 和 `0x1B.Tasks` 同源；`0x02 TaskList` 不参与本状态机。

离线 `EventLogBatch` 是有序命令流。固件按实际发生顺序写入并发送 Records；不得按 RTC Timestamp 排序。App 按线序逐条处理并逐条回 `0x1B`，固件用各自的 Action+OperationID 匹配离线 pending 记录。App 侧采用写前账本：pending 落盘后，按“专注历史 → 清 active 标记 → 任务/宠物状态 → committed”完成事务；中途退出时，相同请求会恢复补做。当前协议没有固件 apply ACK，App 不会静默淘汰 committed OperationID。

#### BLE 数据接收

简单命令使用 3 字节头 (type + length)，大数据使用 **11 字节分包头**（v2.5.24 起，`Seq`/`Total` 各 2B BE；详见 BLE通信协议规格文档 Section 3.2）。

```c
void on_ble_data_received(uint8_t* data, size_t len) {
    if (len < 3) {
        return;
    }

    uint8_t type = data[0];
    uint16_t payload_len = (data[1] << 8) | data[2];
    if (len != 3 + payload_len) {
        return;
    }

    uint8_t* payload = &data[3];

    switch (type) {
        case 0x10: // DayPack (分包重组后)
            parse_day_pack_into_latest(payload, payload_len);
            if (!epd_refresh_in_progress && !task_action_pending) {
                refresh_overview_from_latest_day_pack(REFRESH_FULL);
            }
            break;
        case 0x11: // TaskInPage
            parse_task_in_page(payload, payload_len);
            show_task_in_page();
            break;
        case 0x1B: // TaskListSnapshotAck
            // 先校验 Action+OperationID 与 pending，再校验 StateEpoch+Revision；
            // 全部通过后一次性替换 Overview 清单。
            handle_task_list_snapshot_ack(payload, payload_len);
            break;
        case 0x13: // SmartReminder
            parse_smart_reminder(payload, payload_len);
            show_reminder_banner();
            break;
        // ...
    }
}
```

DayPack / TaskInPage / CustomAvatarFrame 可能以 **11 字节分包**到达。普通帧按 `MessageId + Seq + Total` 分槽重组（Seq/Total 各 2B BE，总数上限 65535）。`0x15` 则在 Seq=0 建立临时文件，校验每片 CRC16 后顺序落盘，不在 PSRAM 里重组整张 KRI。头像传输期间其他 MessageId 仍可交错到达。App 不支持分片 ACK/单片重传；固件发现缺片、CRC 错、乱序或超时时丢弃当前临时文件，保留 committed 旧图，等 App 从 Seq=0 整张重发。secure 模式先逐片校验 SecureEnvelope 时间戳、nonce 和 HMAC，再把解封后的完整 11B 分片交给同一写入器。

`0x1B` 随 TaskCount/文本长度可能超过当前单次写入上限，固件必须同时支持简单包和通用 11 字节分包重组。即使分片使用 GATT withResponse，也只能视为传输完成；任务业务状态仍以完整解析后的 `0x1B` 为准。

**DayPack 刷新合并（v1.9.2）：** `epd_refresh_in_progress` 为真时，完整解析后的 DayPack 覆盖 `latest_day_pack`，不加入 FIFO 刷新队列。当前 EPD 刷新结束后，若有较新的缓存，最多再全刷一次最新内容。当前日程开始或结束由 RTC 和缓存日程本地切换，不能等 App 再发包。在线 Complete/Skip 的 TaskIn/pending 规则不变：最终 DayPack 只换后台缓存，仍由匹配 `0x1B` 一次提交。

**TaskIn 等待计时（v1.9.2）：** 发送 `EnterTaskIn` 前先看 BLE 是否有活跃连接；无连接立即本地执行。有连接时启动独立 5 秒计时器，收到匹配 `TaskInPage` 取消计时并进入任务页；超时清除等待态、走本地兜底或回 Overview/Interactive，并保留事件供后续有限重试。这个计时器不依赖 App 握手、写回调或 iOS 前后台状态。

**静态反馈专项取证（#26，App 侧无法验证，只能真机）：**

「设备静态反馈」是本规格里**唯一一条 App 与浏览器模拟器都测不到**的约束——它是物理器件行为，必须真机逐项取证：

| 取证点 | 方法 | 通过标准 |
|-------|------|---------|
| **无声音** | 安静环境下完成 / 跳过 / 进出屏保 / 进出总结各一次，全程录音 | 录音中**无任何设备发声**（蜂鸣、咔哒、提示音） |

- 证据**不得包含用户原始任务标题、备注、日程名称**或任何伴侣文案正文。需要标识任务时只记 TaskId、OperationID、版本号、长度和结果码。
- 证据**不得包含** `BLE_SHARED_SECRET`、API key、账号 token 或其他凭据。
- 截图含真实内容时先用测试数据复现，或对文本区打码。
